# Releasing

[English](releasing.md) · Русский

## Как это устроено

```
feature-ветка ──PR──► main ──► Release Please открывает «release PR» ──merge──► тег vX.Y.Z + GitHub Release ──► publish.yml
```

- `main` — единственная долгоживущая ветка. Любое изменение попадает в неё через pull request.
- Коммиты следуют [Conventional Commits](https://www.conventionalcommits.org/). Release Please (режим одного пакета) читает их и держит один открытый **release PR**, который обновляет `version.txt`, свой манифест и changelog.
- Release PR также обновляет версию в примерах из `README*.md` и `docs/configuration*.md`: каждый такой блок кода стоит между `<!-- x-release-please-start-version -->` и `<!-- x-release-please-end -->`, а Release Please читает эти файлы как `extra-files` с updater-ом `generic`. Новый пример с версией ArchGate оборачивай так же.
- В `version.txt` лежит последняя выпущенная версия, до первого релиза это `0.0.0`. Между релизами сборки имеют вид `X.Y.Z-SNAPSHOT`.
- Merge release PR создаёт тег `vX.Y.Z` и GitHub Release.
- Публикацию тег напрямую не запускает. Релиз, созданный через `GITHUB_TOKEN` workflow, не вызывает события `release`, поэтому локальный для проекта workflow `publish.yml` запускается по `workflow_run` от workflow Release Please. Он:
  1. забирает коммит, который собрал запуск Release Please (`workflow_run.head_sha`), и ищет на нём тег `vX.Y.Z`; запуск без релизного тега, например обычный push в `main`, тихо завершается без публикации;
  2. проверяет, что `v$(cat version.txt)` равно тегу;
  3. собирает релиз без секретов (`build` без `mavenIT` и parity-теста, которые CI уже прогнал на `main`);
  4. выполняет `publishAndReleaseToMavenCentral` для всех артефактов с подписью и ждёт, пока Central сообщит, что развёртывание опубликовано;
  5. только после этого выполняет `publishPlugins` в Gradle Plugin Portal, так что Portal никогда не ссылается на артефакты, которых ещё нет в Central.
- Секреты передаются только шагу публикации, а job работает в окружении `release`.
- Релизная сборка (`-Prelease=true`) отказывается публиковать без ключа подписи и останавливается с сообщением, в котором названо недостающее свойство `signingInMemoryKey`.
- Чтобы опубликовать вручную, запусти workflow через `workflow_dispatch` с тегом, например `v0.1.0`. Несуществующий тег роняет запуск.

## Первый релиз

Первая версия — `0.1.0`. Её задаёт коммит, в сообщении которого есть footer `Release-As: 0.1.0`:

```
git commit --allow-empty -m "chore: release 0.1.0" -m "Release-As: 0.1.0"
```

Дальше Release Please выводит версии из типов коммитов: `fix` повышает patch, `feat` — minor, breaking change (`!` или footer `BREAKING CHANGE`) — major.

## Обычный релиз

1. Влей изменения в `main` через pull request-ы.
2. Открой release PR, который ведёт Release Please, и проверь changelog и новую версию.
3. Влей его. Создаются тег и GitHub Release.
4. `publish.yml` публикует и выпускает артефакты в Maven Central, затем публикует Gradle-плагин. Следи за запуском; когда он зелёный, релиз вышел.

## Исправить что-то до выхода релиза

Release PR — лишь предложение. Влей исправление в `main` обычным pull request; Release Please сам обновит release PR. Ничего не нужно переносить через cherry-pick.

## Hotfix уже выпущенной версии

Release Please выпускает релизы из `main`, ветки сопровождения не поддерживаются. Влей исправление в `main` как pull request с типом `fix:` и влей следующий release PR. Если в `main` лежит невыпущенная работа, которая пока не должна уйти, не вливай её в `main`, пока она не готова, например держи её в невлитом pull request.

## Откат плохого релиза

Считай опубликованную версию неизменяемой. Никогда не переопубликовывай, не удаляй и не переставляй тег `X.Y.Z`: потребители и их кэши могут уже держать её. Вместо этого **откатывайся вперёд**.

| Цель | Что делать |
|---|---|
| Разблокировать потребителей прямо сейчас | Они закрепляют предыдущую версию, например `1.4.1`. |
| Убрать изменение | Влей в `main` коммит `fix:`, который его откатывает, затем влей release PR. Потребители переходят на `1.4.3`. |

Не двигай и не переиспользуй тег. Если релиз не опубликовался, потому что `publish.yml` упал после создания тега, исправь причину и опубликуй тот же тег ещё раз (см. следующий раздел); не создавай новый тег для той же версии.

## Когда падает `publish.yml`

| Что упало | Что делать |
|---|---|
| Проверка тега | `version.txt` и тег не совпадают. Не публикуй. Исправь процесс release PR, затем выпусти следующий патч. |
| Сборка релиза | Ничего не опубликовано. Исправь причину в `main` и выпусти следующий патч или, если сбой был случайным, перезапусти упавший запуск. |
| `publishAndReleaseToMavenCentral` | Если Central не опубликовал развёртывание, ничего не выпущено: исправь причину (учётные данные, ключ подписи, namespace) и перезапусти упавший запуск. Если развёртывание опубликовано, но истекло ожидание, проверь Central Portal и действуй как в следующей строке. |
| `publishPlugins` | В Maven Central релиз уже есть, поэтому перезапуск всего запуска упадёт на существующей версии. Исправь учётные данные Plugin Portal, затем запусти workflow вручную с тегом и отмеченным `plugin-portal-only`. |

Если публикация не сможет пройти никогда и ты отказываешься от `X.Y.Z`, выпусти следующий патч.

## Предварительные условия (однократно, действия владельца)

- Подтвердить namespace `dev.quokkify` в Central Portal (DNS TXT-запись).
- Создать API-ключ Gradle Plugin Portal.
- Создать окружение `release` и добавить в него секреты: GPG-ключ подписи и passphrase (`SIGNING_IN_MEMORY_KEY`, `SIGNING_IN_MEMORY_KEY_PASSWORD`), токен Central Portal (`MAVEN_CENTRAL_USERNAME`, `MAVEN_CENTRAL_PASSWORD`), ключ и secret Plugin Portal (`GRADLE_PUBLISH_KEY`, `GRADLE_PUBLISH_SECRET`).
- Защитить `main`: только pull request-ы с обязательными проверками статуса.
